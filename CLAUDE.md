# Nonprofit Policy Builder

GRC project. A single-page web app (`index.html`) where a small nonprofit answers a short questionnaire and gets six tailored, plain-English security policies:

1. Acceptable Use
2. Security Awareness and Training
3. Passwords & MFA
4. Data Protection
5. Backup & Recovery
6. Incident Response Plan (may run onto a second printed page; the user's choice, November 2026)

It also produces six forms: the **Onboarding Checklist**, the **Offboarding Checklist**, the **Policy Acknowledgment Form**, the **Asset Inventory**, the **Framework Summary** (see "How the code works") and the **Incident Contact List**. It is not a policy. It changes more often and is more sensitive, so it is kept separate:
- The sheet has its own owner (the primary IT contact), a "last verified" date, a check every three months and a Verification log at the bottom. The policies are reviewed yearly.
- The Incident Response Plan names only the incident lead and the alternate incident contact (plus the board chair, by name only, in its Notify step), and points to the sheet. All other phone numbers and provider details belong on the sheet, not in the plan.
- The sheet adds the insurer row only when the nonprofit has cyber insurance, and the payment processor row only when it takes cards or online donations.
- It prints on exactly two Letter pages with every optional row showing (decided November 2026, when the rows outgrew one page). Page 1 holds the note, People, Systems and providers, and Money, insurance and legal (moved up at the user's request, November 2026, to fill page 1); `div.eyebrow.pagetwo` forces page 2 (Outside agencies; Keep it current; Verification log) in print and, through `PASTE_STYLES`, in Word. Both pages say "Page 1 of 2" / "page 2 of 2", and the note says to print double-sided. Page 1 must not overflow (a third page means it did). The Incident Response Plan may run onto a second page (the user's choice, November 2026, after the review additions pushed the approval block over). After adding content to either, print-preview it. Both are wrapped in `.onepage`, which the compact print styles target.
- The "More" menu ("Print or copy several…") lists the six forms alongside the policies, and all twelve start ticked. Including the sheet was decided, so don't remove it.
- Bank accounts are recorded by last 4 digits only. Never add fields for full account numbers or passwords.

## Audience
Any small nonprofit, including volunteer-run teams with no IT staff, personal devices, shared logins and high turnover. Write in plain English, short sentences, no jargon.

### When a framework version changes
The app never fetches framework data. `_headers` blocks all network calls, and the privacy design depends on that. Updates are made by hand and reviewed by a person. Check for new CIS Controls and NIST CSF versions at each yearly template review.
1. Get the new version's change log or old-to-new mapping from cisecurity.org or nist.gov.
2. Update the version names in `FRAMEWORKS` in `frameworks.js`, and its web addresses (`cisUrl`, `nistUrl`) if the new version has its own page. The builder's footer and `how.html` read them from there, and so does the NIST framework name in the "Before you start" panel (`data-fw="csf"`). That panel says "CIS Controls" with no version on purpose.
3. Update the `POLICIES` labels in `app.js` for any renumbered, moved or removed Controls, and the mapping table and "What each label means" table in `how.html` (and its copy in `assets/framework-labels.md`, including the version names in its intro).
4. Update the mapping table, the IG1 gaps list and the version numbers in this file, and the framework versions in `NOTICE`'s "Third-party material" section (check the new version's license too).
5. Check new or changed IG1 Safeguards. Add plain-English policy lines for any the policies should now cover.
6. Update the project plan: search it for "v8.1" and "CSF 2.0" and update every match.
7. Update the "Template wording last reviewed" date in the `index.html` footer.
8. Run the render test and check that the footer shows the new version.

The footer in `index.html` shows "Version 1.0.0 · Template wording last reviewed <month year>". Update the date after each annual content review.

- Copy buttons put formatted HTML (plus a plain-text version) on the clipboard, so pasting into Word or Google Docs keeps headings, tables and borders. `pasteHTML()` inlines styles from `PASTE_STYLES`, removes highlights, and turns CSS-grid layouts (`.docmeta`, `.sig`) into tables. Word ignores `border-spacing`, so `.sig` uses empty spacer cells to keep the signature lines apart; don't go back to cell spacing. When adding a new styled element, add its pasted style there too.
